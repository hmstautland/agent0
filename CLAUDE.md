# agent0

A local-first AI agent: FastAPI web UI + CLI, a multi-step tool-calling agent loop, and local-only models (Ollama for text, Kokoro for speech, faster-whisper for transcription). **No external AI models in the runtime** (no hosted chat/LLM APIs of any kind) — `core/llm.py` only talks to a local Ollama server.

Read this file before re-exploring the codebase from scratch. It's a fast-moving repo (TTS in particular has been rewritten more than once) — if something here looks stale, trust the code and update this file rather than assuming the file is wrong and re-deriving everything.

## Architecture

```
User (CLI / web UI / voice)
    -> agent.py: _run_steps (multi-step tool loop)
    -> core/permission.py: approve/deny (config/settings.py RULES)
    -> tools/*.py, declared in tools/registry.py
    -> core/llm.py -> Ollama (qwen3 for direct answers, qwen3-coder for the tool loop)
```

- **`core/ui.py`** — FastAPI app assembly: mounts `/static`, `/media`, `/favicon` (saved audio at `/audio/<file>` is *not* a mount - it's a login-protected route in `features/audio/routes.py`); includes `agent_router`, `speech_router`, `logout_router`, then `public_router` last (it has a catch-all route, so anything after it would be shadowed).
- **`agent.py`** — the agent loop (`_run_steps`, shared by CLI's `run_agent` and the web's streaming `stream_agent`). Tries a local-only answer first (`try_local_answer`, structured output), escalates to the tool loop if the model says it needs tools. The tool loop uses Ollama's built-in tool calling over the local `/api/chat` (`core/llm.chat`, schemas from each registry entry's `parameters`), with fallbacks for calls the model writes into its text (qwen3-coder `<function=...>` markup, or JSON). Tool exceptions and Ollama errors are handed back to the model / sent as an `error` event, not raised. Both LLM calls in the loop go through `core/llm.chat_stream` (`message = yield from chat_stream(...)`), which yields `llm_delta` events (`kind`: `thinking`/`content`) shown live beside the thinking image in the web UI; tests stub it via `fake_chat` in `tests/test_agent_flow.py`. `core/llm.chat` is the non-streaming variant. History is kept inside the code model's window by `core/context.py`: `cap_result` cuts one oversized tool result when it's added, and `prune_messages` stubs the oldest tool results (newest 2 stay whole) before each model call - the model gets a pruned copy, `run.messages` stays full. No LLM summarizing, by design (a summary can lose the exact text `edit_file` needs; add one only if pruning proves too lossy); `OLLAMA_NUM_CTX` (light, 8192) and `OLLAMA_CODE_NUM_CTX` (code, 32768) are separate.
- **Approvals (`core/runs.py`, `core/permission.needs_approval`)** — a call that needs approval parks the whole run in memory under a fresh single-use `run_id`, owned by the login session. The permission card posts only `run_id` + decision; `resume_agent` runs exactly the parked call and continues the same run (no replay from step 0). Tools marked `external` ask once per login session (`request.session["external_grants"]`, cleared on logout; CLI: per process) and ignore RULES `"auto"`. `SESSION_SECRET` (≥32 chars, from `.env`) is required by `core/ui.py`; `tests/conftest.py` sets a throwaway one.
- **`storage/`** — persistence, kept apart from what the data means: `db.py` (`DB_PATH` = `local_storage/agent0.db`, `AGENT0_DB` to override; `with connect() as conn:` opens one connection per call, applies `schema.sql` when `PRAGMA user_version` < `SCHEMA_VERSION` - bump it when changing the schema, statements must be re-runnable), `schema.sql` (tables + the FTS5 index `turns_fts`, kept in step by triggers), `conversations.py` (`save_turn`, `recent_turns`, `search_turns`; `fts_query` quotes each word so user text can't inject FTS5 syntax). New stored data gets its own `storage/<name>.py`.
- **Conversation memory (`core/conversations.py`, stored via `storage/`)** — one conversation per login session (`request.session["conversation_id"]`; CLI: per process), reset by the "+" button (`POST /conversation/new`) / CLI `/new`, and by logout. Every finished request is stored as a turn (question, final answer, one-line summaries of the tool calls that ran, `AgentRun.actions`) via `conversations.record`, which wraps the event stream in `stream_agent`/`resume_agent`/`run_agent` and the route shortcuts (`core/agent_routes.shortcut_events`). The newest turns (budgeted by `HISTORY_TURNS`/`HISTORY_CHARS`) go between the system prompt and the question in both the local-first call and the tool loop - as plain user/assistant text with a `[Tools used: ...]` line, never tool results. Earlier sessions: the low-risk `search_history` registry tool (FTS5, best match first). Tests get a per-test DB from the autouse `conversation_db` fixture in `tests/conftest.py`.
- **`tools/registry.py`** — the tools the *LLM* can choose to call (file read/write/edit, web search, calendar). Each tool's risk level gates whether it needs approval; `config/settings.py`'s `RULES` overrides that per-action.
- **TTS/STT generation is NOT in `tools/registry.py`** — both STT (`/speech`, mic button) and TTS generation (`/tts*`, speaker button/dashboard) are direct UI actions that bypass the LLM/permission loop entirely, wired straight from `static/speech.js` / `features/audio/static/tts.js`. This is deliberate, not an oversight — don't "fix" it by moving them into the registry unless asked.
- **`core/speech_to_text.py`** — faster-whisper, local.
- **`features/calendar/`** — all calendar logic: `calendar.py` (events, create-command parsing, month payload, `is_calendar_request`; the "add a meeting ..." chat shortcut is `create_event_from_command`, used by both `agent.py` and `core/agent_routes.py` - it replies asking to restate instead of raising, and returns a `show_calendar` with the new event's `day` to highlight), `routes.py` (`GET /calendar/month`, static at `/static/calendar`), `static/` (month-grid UI). Chat shortcuts (`core/agent_routes.py`) and the agent loop (`agent.py`) emit a `show_calendar` event / `calendar_month` template var; the page fetches its own data. Don't re-add calendar helpers to `core/`. Feature folders: mount their static dir *before* `/static` in `core/ui.py`, and add its template dir to `TEMPLATE_DIRS` in `core/templates.py` and its static mount to `MOUNTS` in `tools/verify.py`. `templates/index.html` only *includes* partials: each feature provides `<name>/head.html`, `<name>/scripts.html` and its own cards; shared pieces live in `templates/components/` (`permission_card.html` is one card used by both the streamed and plain `/ask` flows).
- **`features/audio/`** — everything audio-output lives here (feature folder: Python, routes, `static/`, `templates/audio/`): `text_to_speech.py` (Kokoro-82M based TTS), `routes.py` (`audio_router`, mounted in `core/ui.py`, plus its static files at `/static/audio`), `player.py` (see below). `core/speech_routes.py` now only holds STT (`/speech`). TTS with multiple endpoints (`/tts`, `/tts/voices`, `/tts/dialogue`, `/tts/convert`, `/tts/extract-text`, `/tts/files`). Full details (voices, env vars, ffmpeg requirement for MP3/OGG, dialogue script format, document drag-and-drop + Markdown flattening) are documented in **README.md's "Text-to-Speech" section** — read that instead of re-deriving it from the source.
- **`features/audio/player.py`** (`play_audio_file`) — the one exception to "speech isn't a registry tool": finding and "playing" an already-saved file from `local_storage/audio/` by (partial) name or by number *is* a real `tools/registry.py` entry, because it's a genuine LLM-invokable action, not a media-generation pipeline. It's also given the same reliability shortcut as calendar/notes (`parse_play_command`, checked directly in `agent.py::_run_steps` and `core/agent_routes.py::audio_play_result`, both `/ask` and `/ask_stream`) since the local model can't be trusted to reach for it on its own. A "choose between several matches" result is *not* plain text - it rides along as a structured `audio` field on the `final_response` event (see `features/audio/static/audio-player.js` / `features/audio/templates/audio/audio_play.html`), rendered as clickable buttons that just resubmit `"play number N"`. The candidate list for "number N" is process-local, in-memory state (`features/audio/player._last_candidates`) - same single-user tradeoff as `core/speech_to_text.py`'s recording globals, not safe across concurrent users or a restart.

## Running things

```
source venv/bin/activate.fish   # or venv/bin/activate for bash
pip install -r requirements.txt
ollama serve                    # usually already running as a systemd service
uvicorn core.ui:app --reload    # web UI at http://127.0.0.1:8000
python -m agent                 # CLI mode
python -m pytest                # test suite (bare `pytest` can't import the project modules)
```

Full setup/model details (which Ollama models to pull, env vars, Windows instructions) are in README.md — don't duplicate them here.

## Conventions worth knowing before editing

- `write_file`/`edit_file` (in `tools/files.py`) back up the previous version to `local_storage/backups/<timestamp>/<path>` before writing (one backup per write, so history is not limited to one level; gitignored with `local_storage/`) — this is intentional, not garbage to clean up. Nothing prunes old backups yet.
- After changing a template or static file, run the `verify_app` tool (`tools/verify.py`) — it compiles templates, resolves `{% include %}`, checks referenced `/static`/`/media`/`/favicon` files exist, and re-imports `core.ui`. The system prompt (`config/system_prompt.py`) already tells the LLM to do this for its own edits; do the same when editing by hand.
- `local_storage/` is gitignored, holds runtime state (notes, generated audio, `logs.txt`). `local_storage/logs.txt` is a JSONL event log (`core/logger.py`) that prunes itself past 1 MB (older than 14 days first, then oldest; `python -m core.logger` prunes by age now) — still ~1000+ lines, so `tail`/`grep` it, never read it in full.
- Downloaded model weights live under `models/` (gitignored) and are fetched lazily on first use, not at import time — don't try to pre-load them or make startup depend on them.
- `tests/` mirrors the module layout (`test_agent_flow.py`, `test_web_tools.py`, `test_speech_routes.py`, `test_text_to_speech.py`, `test_audio_tool.py`, ...) — check for an existing test file before assuming a module is untested.
